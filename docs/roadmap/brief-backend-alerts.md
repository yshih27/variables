## PR B — watches, signals, digests, notifiers
1. **Schema** (`supabase/migrations/2026092500000{1,2}_alerts.sql`, RLS on, no anon policies, PII-guarded like `subscribers.ts`): `report_subscribers.manage_token text unique` (issued on first watch; the link a reader manages alerts by, never the unsubscribe token); `alert_subscriptions` (`id uuid`, `subscriber_id` → `report_subscribers`, `entity_type` ∈ `identity | ip | platform`, `entity_key` text (an identity slug, an ip key, a platform key), `kinds` text[] ⊆ `floor | volume | clear | listing`, `channel` ∈ `email | telegram`, `created_at`, `paused_at`, unique on (subscriber, entity_type, entity_key, channel)); `alert_state` (`subscription_id`, `key` text, `value` jsonb, `updated_at`; the last floor fired at, the listing set last seen); `alert_events` (`id`, `subscription_id`, `kind`, `fingerprint` text unique, `payload` jsonb, `fired_at`, `sent_at`); `telegram_links` (`subscriber_id` unique, `chat_id` text, `linked_at`). One accessor module, `src/lib/alerts/store.ts`, is the only thing that touches these tables.
2. **The signals** (`src/lib/alerts/signals.ts`, pure over their inputs so the unit tests drive them with fixtures), each producing `{ kind, entity, payload }` where the payload carries every figure WITH its window and source, never a bare number:
   - `floor` (identity only): the identity's floor under the page's rule (plausible asks only, else no floor) against the floor last fired for this subscription (`alert_state`); fires on a move of ≥ 10% either way, or a floor appearing/disappearing; the payload carries both floors, the venue, the reference price and its month.
   - `volume` (ip, platform): the last COMPLETE day's `volume_usd + gacha_volume_usd` (source-complete days only, INV-8) against the mean of the seven complete days before it; fires at ≥ 2× with the base ≥ `DELTA_MIN_BASE_USD`; the payload carries the day, the mean, the window and the split (resale vs pack spend; the Claw for Beezie).
   - `clear` (identity, ip, platform): a sale in the secondary-sales store since the last run that is ≥ 3× the identity's reference price (identity watches) or ≥ $1,000 (ip / platform watches; a constant in one place, named, not typed into copy); the payload carries the card, the price, the venue, the time and the reference it is measured against.
   - `listing` (identity only): a slab of the identity present in `listings.byItem` that was not in the subscription's last-seen set; the payload carries the ask, the venue, whether it is plausible under the page's rule (an aggregator placeholder is reported as an unverified ask, never as "listed at $1"), and the identity's reference.
3. **The run** (`scripts/run-alerts.ts`, `npm run run-alerts`; `--dry-run` DEFAULT prints what would fire and to whom, `--send` performs): load active subscriptions of confirmed, not-unsubscribed subscribers; evaluate every signal once per entity (not per subscription) from ONE read of each source; dedupe with `fingerprint = <subscription>:<kind>:<entity>:<UTC day>` (one event per kind per entity per subscriber per day); then compose ONE digest per subscriber per run (never an email per event) and hand it to the notifier; record `sent_at`. Scheduled in the 6-hourly core batch after `warm-listings` and `warm-core-dune`, guarded the same way as the sender. Budget: the whole run under 60 s at 1,000 subscriptions; report the measured time.
4. **The notifiers** (`src/lib/notify/`): one interface `Notifier.send(subscriber, digest)`; `email.ts` renders the digest (`src/lib/email/templates.ts` gains `alertDigestEmail`: the subject names the count and the biggest move; each event is one line with its figures and windows and a link to the page; the `List-Unsubscribe` headers ride along; a `manage alerts →` link with the manage token); `telegram.ts` posts the same digest as one message via the Bot API (`TELEGRAM_BOT_TOKEN`; absent → the channel is `unavailable` and nothing is attempted). Linking: `GET /api/alerts/telegram/start?token=<manage_token>` answers a deep link `https://t.me/<bot>?start=<one-time code>`; `POST /api/alerts/telegram/webhook` (secret path segment from env) receives `/start <code>` and stores the `chat_id`. Test both notifiers through an injected transport; the Telegram path is verified against the real bot only if the token exists in your env (it does not in the orchestrator's; say so).
5. **The routes** (same-origin, rate-limited like `/api/subscribe`, honeypot on the create, the generic answer on anything that could reveal an address): `POST /api/alerts` `{ email, entity_type, entity_key, kinds, channel, website? }` → for a new address, the double opt-in confirmation email first (the watch is stored, and stays inactive until confirmed); for a confirmed one, the watch and a `manage` link by email; always `{ ok: true, message }`. `GET /api/alerts?token=<manage_token>` → the subscriber's watches (entity labels resolved from the naming SSOTs, never the raw keys alone). `POST /api/alerts/update` `{ token, id, action: pause | resume | delete }`. `GET /api/alerts/channels` → which channels exist in this deployment (email always; telegram when the token is set), so the frontend never offers a channel that cannot deliver.
6. **Privacy.** No email, token or chat id in any log line (count and kind only). The manage token is the only key to a subscriber's watches; unknown token → the same neutral page as `/api/confirm`. Retention follows `SUBSCRIBER_UNSUBSCRIBE_MODE`; an unsubscribe deletes or marks the watches with the subscriber, in the same call.
7. **Tests** (`test:alerts`): each signal on fixtures (threshold both sides, the noise floor, the plausibility rule on a placeholder ask, an appearing and a disappearing floor); the fingerprint dedupe across two runs on one day and across midnight; one digest per subscriber from N events; the templates render every figure with its window and no figure that is not in the payload (assert on the rendered text); the Resend headers; the store's manage-token issue is idempotent.

## Constraints
No copy beyond the templates and the API messages, and in them: figures only from payloads, each with its window and source; "the Claw" for Beezie's machine, never gacha in a Beezie line; a receipt line, never a banner. One accessor per PII table. Zero production writes: migrations are files, `run-alerts` and `send-weekly-report` are dry-run by default, and the orchestrator runs them. No new colours, no new estimators: a floor is the page's floor, a reference is the page's reference.
