# Executor WP — search rows, the 1999 Base Set alias, and the panel at the core cadence: three small backend PRs

Backend executor, Varible. THREE PRs off `origin/main`, each mergeable alone, in this order of value: (A) `perf/search-rows`, (B) `data/base-set-alias`, (C) `ops/panel-cadence`. Own worktree with the three symlinks; never write to production from an executor (`--out=<dir>` builds, `--dry-run` defaults, `--apply`-gated scripts, `SNAPSHOT_LOCAL_DIR` for every probe); a migration is a FILE in the PR, applied by the orchestrator (there is no DDL path from any session: the user pastes it into the Supabase SQL editor); tsc/eslint clean; truthful trailer. None of these computes a new number. They make an existing one faster, one identity honest, and one page timelier.

## What exists (build on it, do not re-derive)

## PR A — the search rows persisted, and a trigram index under the ILIKE
1. `warm-sale-panel` persists a fourth derived blob, `search-rows`, from the same run and the same panel as the other three: the output of `buildIdentitySearchRows()` and of the character rows (`readCharacterSearchRows`'s shape), gz-packed with the run's `generatedAt` and the panel row count, the same pattern as `packIdentityIndex`. `readIdentitySearchRows` and `readCharacterSearchRows` read THAT blob through their in-process memo and fall back to today's build only when it is absent, saying so on the console (the pattern `slugIndex` uses). The rows are the compact shape the palette already uses (`slug`, `label`, `sub`, `href`, `haystack`, `sales30d`, `slabs`); measure the blob's gz size and its inflate time.
2. `supabase/migrations/20260929000001_cards_name_trgm.sql`: `create index if not exists cards_name_trgm_idx on public.cards using gin (name gin_trgm_ops);` with a header saying it is applied by hand in the SQL editor, outside a transaction is not possible there so it is a plain `create index` (137K rows: seconds, blocking writes for that long; run it between batches, and say so). `searchCardsByName` keeps its shape: `ILIKE '%q%'` is exactly what a trigram GIN accelerates, so no query change; if PostgREST's `.ilike` cannot use the index for some reason, say so with the evidence rather than changing the query to something the index needs.
3. `/api/internal/search` gains a `Server-Timing` header (`cards;dur=…`, `identities;dur=…`, `characters;dur=…`, `metrics;dur=…`, `total;dur=…`), so the before and after can be read from production with one curl by the orchestrator, and every later regression is visible in the browser's network panel. Nothing else about the route changes.
4. `check-freshness`: `search-rows` joins the indices-batch derived blobs list under the `price-index` rule.
5. Measure on a COLD `next start` (not dev) with `SNAPSHOT_LOCAL_DIR`: `/api/internal/search?q=charizard` and `?q=pikachu psa 10`, first hit and second hit, before and after, from the `Server-Timing` values; the blob sizes; the memory of the process after the first query (`process.memoryUsage().rss`, printed once).

## PR B — Beezie's "Game" is the 1999 Base Set: an alias, after a shadow re-key
1. **The methodology call, made here so you implement rather than decide:** PSA's `1999 POKEMON GAME` label IS the 1999 Base Set, and the print-run distinction the JUNK note protected (1st Edition, Shadowless, Unlimited) already lives in the identity's `edition` field, so pooling `Game` under `base-set` does not merge different print runs. Guard: a `Game` / `Pokemon Game` string whose title carries a year other than 1999, or `Base Set 2`, must NOT alias (it stays junk; report the count). The alias applies to `pokemon` only.
2. In `setName.ts`: `game` and `pokemon-game` leave `JUNK` and enter `ALIASES` → `base-set` (name `Base Set`), IP-scoped if the map is flat today (add the smallest hook that lets an alias name its IP; every existing entry stays IP-free). 3. **The shadow build FIRST, no production write:** `warm-sale-panel.ts --out=<dir> --shadow-rekey` generalised so OLD = the panel's rows keyed by the code on `main` and NEW = this branch's extractor (today it compares v4.1 with v4.2; keep that mode working and add this one, `--shadow-rekey=alias` or the flag you prefer, named in the report). The report the PR carries: identities merged (expect the 688 `pokemon/game/` slugs and the 65 `base-set` ones to become one family; give the number), the 30 largest merges by sales with their raw set strings, edition, number and grade so a FALSE merge (two different cards under one key) is visible, and how many you judge false and why; the fragment count before and after; per published entity per month, identities priced and the level (old → new, delta in pp) for `ip:pokemon`, `set:pokemon:base-set`, its category and `market:total`; thin flags that appear or disappear; grade-premium pairs and the Charizard character rollup before and after. 4. **The cutover pieces, unapplied:** the `method-changes` entry (`v4.3`, summary "Beezie's Game and Pokemon Game labels keyed as the 1999 Base Set", the entities and months that moved, from the shadow report) so `/methodology` renders the before/after from data; the 688 old slugs registered as aliases the way the v4.1 forms were, so every old URL 301s on the page routes and answers `canonical: false` on the API; `backfill-card-identity-key.ts --rewrite` unchanged (it already recomputes from the extractor). ## Constraints
No copy. No new estimator: a floor is the page's floor, a reference is the page's reference. Zero production writes: `--out`, `--dry-run`, `--shadow-rekey` and migrations-as-files; the orchestrator applies and runs. No top-level await in `scripts/**`. The `Server-Timing` header carries durations only, never a query or a count that could name a reader. A re-key is a method change and ships with its ledger entry, or it does not ship.
