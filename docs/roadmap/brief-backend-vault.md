# Executor WP — your vault, valued, backend: a wallet in, every slab priced by the same rule as its page

Backend executor, Varible. One PR fresh off `origin/main` (e.g. `feat/vault-backend`), pushed, opened against main, NO merging. Own worktree with the three symlinks; never write to production from an executor (`--out` modes, `SNAPSHOT_LOCAL_DIR`, dry runs and `--apply`-gated scripts only); tsc/eslint clean; truthful trailer. Design: bet 2 in `docs/roadmap/features-roadmap.md`. The bet is "portfolio apps make people type their collection; we read it", so the whole value is in reading the chain honestly and pricing by the rule the site already publishes. No new estimator, no new floor rule, no number the identity page would not print.

## What exists (build on it, do not re-derive)
- Prices: `src/lib/data/identityDetail.ts` — `cachedPanel()` (the sale panel, in-process memo), `slugIndex` / `IdentityIndexSnapshot` (`slabsByKey`: identity key → the slabs' `<code>-<tokenId>` ids), `cachedListingIndex()`, and `buildDetail` which computes, per identity, `monthly` (`monthlyIdentityPrices`, latest COMPLETE month, n ≥ `MIN_SALES_PER_IDENTITY`), the last sale, and `floor` with `vsMonthly` + `coverage`. `src/lib/card/identityView.ts` `readFloor` / `latestCompleteMonthly` (the floor rule: an ask headlines only within `FLOOR_VS_MONTHLY_MIN`–`MAX` of the reference). `src/lib/data/referencePrice.ts` is the shape a price has on this site; a vault line must agree with `/api/public/price/<slug>` to the cent.
- The card-to-identity join: `cards.identity_key` / `identity_slug` (migration `20260914`, written by `scripts/backfill-card-identity-key.ts`, not by `cardRowFromMeta`). Per-row derivation for a row without them: `extractCardIdentity({ name, cardName, set, grade, year, cardNumber })` → `identityKey(ip, parts)` / `identitySlug(ip, parts)` — the backfill's lines, verbatim. Card ids: `src/lib/card/ids.ts` (`cc-<mint>`, `bz-<tokenId>`, `pg-<assetId>`, `cy-<tokenId>`), `readCards(platform, tokenIds)` in `cards.ts` (metadata only; you will need the derived columns too).
- Chain reads: `src/lib/helius/client.ts` `dasCall` with its credit meter (`heliusCreditsUsed`, `HELIUS_CREDIT_BUDGET`) and `DasAsset` (owner + metadata inline); `src/lib/rarible/client.ts` `raribleGet` (timeouts, retries, quota 429s) and `src/lib/rarible/queries.ts`; `PLATFORM_SOURCES` for the collection ids (Courtyard `POLYGON:0x251b…`, Beezie `BASE:0xbb5e…`, CC `CCryptW…`, Phygitals' two cNFT trees). Listings: `src/lib/data/listings.ts` `byItem` keyed `POLYGON:0x…:tokenId` / `SOLANA:<mint>`.
- API: `src/lib/api/v1.ts` (`v1Ok` envelope, attribution, CORS, `v1Options`), `src/lib/api/auth.ts` (`rateLimitInMemory`), the `/api/v1/price/[...slug]` route as the template. Tests run with `tsx --test` (see `package.json` `test:*`).

## Scope
1. **The address.** `src/lib/vault/address.ts` `parseWalletAddress(input)` → `{ chain: "solana", address }` (base58 that decodes to 32 bytes) | `{ chain: "evm", address }` (`0x` + 40 hex, lower-cased; a mixed-case input must pass EIP-55 or it is rejected as a typo) | `null`. An EVM address is one address space, so it is read on Polygon (Courtyard) and Base (Beezie) both; a Solana address on Collector Crypt and Phygitals both. No name resolution (ENS / SNS) in this PR.
2. **The holdings.** `src/lib/vault/holdings.ts` `enumerateHoldings(parsed)` → `{ holdings: RawHolding[], partial: { reason: string; after: number } | null }`:
   - Solana: DAS `searchAssets` with `ownerAddress` and `grouping: ["collection", <mint>]`, one query per tracked collection, paginated 1000, keeping the `DasAsset` (owner and metadata ride inline, so a slab the weekly trait crawl has not reached still has a name and attributes). Budget: at most 12 DAS pages per request; past it, stop and set `partial` (`reason: "helius-budget"`). Charge the credit meter as the warmers do.
   - EVM: Rarible `items/byOwner` for `POLYGON:<addr>` and `BASE:<addr>`, filtered to the two collection ids, paginated, at most 12 pages per chain; past it, `partial` (`reason: "rarible-budget"`). If the endpoint cannot filter or 429s in practice, say so in the PR and use `Etherscan tokennfttx` per contract as the alternative — with the note that the key is not in Actions today. Report which one shipped and why.
   - A 20 s wall clock across the whole enumeration; on expiry, `partial` with `reason: "timeout"`. A `partial` result is still returned and still priced; the reader is told what is missing, never shown a total as if it were whole.
3. **The join.** Each raw holding becomes a `VaultHolding` with `cardId`, `platform`, `tokenId`, `name`, `ip`, `set`, `number`, `grade`, `image`, and `identity: { key, slug, href } | null`. Resolution order: the `cards` row's `identity_key` / `identity_slug` (add `readCardRowsByIds(platform, tokenIds)` in `cards.ts` selecting the derived columns; chunked like `readCards`); else the backfill's derivation from the row; else, for a token with no row, from the metadata in hand (DAS inline for Solana via `cardRowFromMeta`; `getBeezieMetadata` for Beezie, which persists as it already does today, capped at 50 live tokenURI reads per request). Courtyard tokens have no `cards` rows and no identity today (bet 5's "Courtyard mints enriched to cards"), so they are listed by their Rarible item name with `identity: null` and `unkeyed: "courtyard-no-card-row"`; every other unresolvable token carries its own reason string. A holding is never dropped for lacking an identity.
4. **The valuation, one pass, one rule.** `src/lib/data/vault.ts` `getVaultValuation(input)` → `VaultValuation | { error: "invalid-address" }`, cached 10 minutes per `(chain, address)` in `unstable_cache` (the payload is small; cap `holdings` at 2,000 rows and set `partial` (`reason: "cap"`) beyond it so it never nears the 2 MB cache limit). Factor the per-identity pieces of `buildDetail` (monthly → latest complete month, last sale, floor with `vsMonthly` and `coverage`) into `valueIdentities(keys: string[])` used by BOTH `buildDetail` and the vault, so the two cannot disagree; it walks the cached panel ONCE for the whole key set. Per holding:
   - `reference: { month, priceUsd, n, thin } | null` — the identity's latest complete-month median (the Varible price), never the running month.
   - `lastSale: { ts, priceUsd, venue, cardId } | null`.
   - `floor: { priceUsd, venue, plausible } | null` — the identity page's rule; `plausible` false when the ask sits outside the band of the reference (else of the last sale); with neither reference nor last sale, `plausible` is false (there is nothing to judge it against).
   - `yourAsk: { priceUsd, source } | null` — this token's own live listing from `listings.byItem`.
   - `value: { usd, basis: "reference" | "last-sale" } | null` — the reference when it exists, else the last sale; a floor is NEVER a value (it is what someone asks, not what anyone paid). `null` with `unvalued: "no-identity" | "no-sale"`.
   - Totals: `holdings`, `keyed`, `valued`, `atReference: { usd, n }`, `atValue: { usd, n }` (reference-or-last-sale — the headline), `atFloor: { usd, n }` (plausible floors only), `spread: { usd, pct, n } | null` = `atFloor − atReference` over the holdings that have BOTH, and `unvalued: { n, reasons: Record<string, number> }`. `byVenue`, `byIp`, `byGrade`: `[{ key, label, holdings, valued, usd }]` on the `atValue` basis, sorted by `usd`. `asOf` = the panel snapshot's `generatedAt`; `method: "v4.2"`.
5. **The endpoint.** `GET /api/v1/vault/<address>` (keyed, attributed envelope, CORS, `v1Options`), rate-limited per key as the other v1 routes are and additionally `rateLimitInMemory` bucket `vault` at 30/min per IP, because every cold call spends third-party credits. `invalid-address` → 400 in the envelope; a wallet with no tracked holdings → 200 with `holdings: []` (an empty vault is a result, not an error). No key-free public endpoint in this PR: the page reads `getVaultValuation` server-side.
6. **Privacy.** An address is public on-chain, but the site must not become a ledger of who looked up whom: no address is written to any table or warmer log; the 10-minute cache is the only state; the v1 route logs the key id and the chain, not the address.
7. **Tests** (`test:vault` in `package.json`): `address.test.ts` — base58 valid / wrong length / EVM checksum pass, fail and all-lower; `vault.test.ts` on a fixture panel — reference beats last sale; last sale used only without a reference; an unplausible floor is never a value and never in `atFloor`; `spread.n` counts only holdings with both; a `partial` result still prices; `byIp` sums equal `atValue`. Plus a parity test: for 25 identities from the live index, `valueIdentities` equals `getIdentityDetail`'s `monthly` tail, last sale and floor field for field.

## Constraints
No copy, no UI (frontend brief). Zero new estimators: the price is `monthlyIdentityPrices`, the floor is `readFloor`'s rule, the join is the backfill's derivation. Zero production writes beyond what `getBeezieMetadata` already does on the identity page. Every third-party read is budgeted and metered, and a budget hit is a `partial` with its reason, never a silent truncation. The address is one input; the chain is detected, never asked.
