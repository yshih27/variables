## The surfaces
1. **Watch identities.** The watchlist gains a third id form, `identity:<slug>`, and the identity page gets the same star `RailActions` gives IPs and platforms (route → id: `/i/<slug>` → `identity:<slug>`); `/watchlist` grows an "Identities" group listing them with the same read the vault uses for a line (name, grade chip, reference price with its month and n, floor when plausible) so a watched card is a priced card. `localStorage` stays the store for the star; nothing here writes to a server.
2. **"Alert me"** beside the star on identity, IP and platform pages: a sheet, not a page. One email field (or the address remembered on this device once confirmed), the kinds that apply to this entity as checkboxes with their thresholds written as receipt lines (`floor moves 10% or more`, `a clear at 3× the reference price`, `daily volume 2× its week`, `a new listing`), the channel picker showing only what `GET /api/alerts/channels` returns (email; Telegram when the deployment has a bot), and one button. Submit → `POST /api/alerts` → the sheet's state says exactly what the API said: for a new address, `check your email to confirm`; for a confirmed one, `watching · manage link sent`. Errors are receipt lines, never banners. The honeypot field rides along as on `SubscribeForm`.
3. **`/alerts`** — the manage page, reached only by the tokenized link in an email (`/alerts?token=…`): `robots: noindex`, `force-dynamic`, never linked from nav. It lists the subscriber's watches as rows (entity with its link and art where it is a card, kinds as chips, channel, paused state) with `pause` / `resume` / `delete` per row, and the retention line from the privacy page in the foot. An unknown or missing token renders the same neutral page the confirm route uses. No email address is printed on the page (the link proves it; printing it would put it on a screen).
4. **Telegram linking** (only when the channel exists): on `/alerts`, a `Link Telegram →` action that calls the backend's start route and shows the deep link as a button and as a copyable line; after linking, the row reads `Telegram · linked`.
5. **The report landings** — carry PR #56 (its two files merge clean on `main`): `/report?confirmed=1` and `?unsubscribed=1` swap the subscribe slot for the acknowledgment, client-side behind a `Suspense` boundary as its body describes, and add `?alerts=1` → `alerts confirmed · manage link sent`. `SubscribeForm` prints the API's message rather than its own success text, so the double opt-in's `check your email` is what a reader sees.
6. **The digest, as the reader sees it.** Render the backend's `alertDigestEmail` and `weeklyReportEmail` HTML in headless Chrome at 600 px (an email client's width) and at 375; every figure must carry its window, every line its link; the brand pair only, system fonts only, no image the client would block. Fix in the template what does not read; say what you changed.
